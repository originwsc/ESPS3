# ⚠️ 强制纪律（违反任何一条立即停止）

1. **严禁超纲**：禁止新增任何 SDD.md 中未定义的接口或字段
2. **严禁自决定**：遇到 SDD 没覆盖的场景，**先停下来用 AskUserQuestion 问用户**，不要自己拍板

5. **资源确定性释放**：连接/句柄/文件等资源必须在使用后确定性释放，避免泄漏
6. **遵循项目 rules.md**：命名、目录、错误处理、提交规范以项目根目录 rules.md 为准

# 实现原则（不分语言，必须满足）

> 这些是结构性要求，用所选技术栈的惯用方式实现，而不是照抄某个框架的代码。

## 配置外置
- 连接地址、密钥、密码等从环境变量或配置文件读取
- 源码中**不得**出现真实密钥/密码的默认值
- 必填配置缺失时启动即报错并给出清晰提示

## 数据访问层
- 所有数据访问统一经过数据访问层，业务层不直接拼查询
- 一律用**参数化 / 预编译**方式传入用户输入，禁止字符串拼接（防注入）
- 写操作按需用事务；连接/句柄用完确定性释放（try/finally 或语言等价机制）

## 鉴权 / 中间件（如适用）
- 受保护接口统一经过身份校验 + 角色校验
- 当前用户信息挂到请求上下文，业务层从上下文取，不重复解析凭据
- 凭据按 rules.md 的方案哈希/加密存储，永不明文

## 统一响应 / 错误
- 全项目统一的返回结构与错误表达（HTTP / RPC / CLI 各按其约定）
- 业务错误返回可读信息，不向调用方泄漏内部堆栈/技术细节
- 每个 except/catch 记录日志，不静默吞异常

## 自测脚本
- 用所选栈的方式（HTTP 客户端 / 单测框架 / CLI 调用）覆盖所有 P0 接口
- 输出清晰的通过/失败标记，失败即非零退出
- 与 TEST.md 的用例对应

# 标准项目结构（示意，按技术栈调整）

```
{{项目名}}/
├── <源码目录>/
│   ├── <配置>
│   ├── <数据访问层>
│   ├── <应用入口>
│   ├── <业务模块...>
│   └── <工具：鉴权 / 统一响应 / 日志>
├── <数据初始化脚本>
├── <依赖清单>
├── README.md
└── <自测脚本>
```

# README.md 必须包含
1. 项目简介（一段话）
2. 环境要求（语言/运行时版本、依赖服务）
3. 安装步骤（依赖安装 → 服务/数据库准备 → 配置 → 初始化数据）
4. 启动命令
5. 测试账号（如有）
6. 常见错误速查表（来自 ARCH.md 安全/开发流程一节）

# 工作流程（Agent 模式逐步执行）

1. **先建项目结构**：按 SDD 模块清单创建目录和空文件
2. **再写基础设施**：配置 + 数据访问层 + 统一响应 + 鉴权（按上面的实现原则）
3. **再写业务**：从一个模块开始，一个模块一个模块来
4. **最后写**：数据初始化脚本 + 依赖清单 + README + 自测脚本
5. **自测**：运行自测脚本，把输出贴出来
6. **报告**：告诉用户「✅ 实现完成，全部 P0 测试通过」并列出每个测试结果

# 自检清单（实现完毕后逐项检查）

- [ ] 程序能成功启动，无报错？
- [ ] 自测脚本全部通过？
- [ ] 所有接口都走统一响应/错误封装？（搜索代码确认无散落的原始返回）
- [ ] 所有数据访问资源都确定性释放？
- [ ] 所有查询都用参数化/预编译？（搜索确认无拼接用户输入）
- [ ] 密钥/密码是否外置（源码无硬编码）？
- [ ] 依赖清单是否锁定主版本？
- [ ] README 是否包含完整启动步骤？
- [ ] 初始化脚本是否有必要的初始数据？
- [ ] 命名/目录/风格是否符合项目 rules.md？
